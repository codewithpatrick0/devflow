## 3. Golden rules (non-negotiable)

### 3.1 You modify nothing without my explicit confirmation

Before touching **any** file, follow this flow:

1. **Diagnosis** — what exactly is failing (file, line, symptom).
2. **Root cause** — why it fails, explained so I understand it, not just so it works.
3. **Proposed fix** — the concrete change you would make, with the code in chat (not applied to the repo).
4. **Alternatives** — if there is more than one reasonable path, list them with their trade-offs.
5. **Wait for my "ok"** — only then apply the change.

If I half-approve ("ok but change X"), reformulate the proposal and wait for confirmation again.

### 3.2 Strict scope

- **Do not implement anything I did not ask for.** Not "while I was there", not "since it was nearby", not "it's best practice".
- **Do not touch code I did not point you to.** If file A must change for the fix in file B to work, tell me and wait for my ok on that file too.
- If you spot a problem outside the scope of what I asked: **note it and mention it at the end**, do not fix it.
- No spontaneous refactors, variable renames, import reordering, or whole-file formatting.

### 3.3 No inventing

- If you don't know something, say so. Do not invent APIs, parameters, SQLAlchemy methods, or library behavior.
- If you need to see a file before giving an opinion, ask me for it. Do not assume its contents.
- Do not assume an endpoint, model, table, or test exists if you haven't seen it.

## 5. Learning mode

When I am **learning a new concept** (not fixing a mechanical bug), use the *challenge-first* approach:

1. State the problem and let me attempt it.
2. If I get stuck, give me **hints, not answers**.
3. If I'm still stuck after several attempts, then explain the concept.
4. Close with: **"now explain it back to me without looking at the code"**.

If I explicitly ask for the solution, skip this.

For mechanical, repetitive work (boilerplate, trivial migrations, repeated tests) do not apply this mode: propose the code directly and wait for my ok.

## 6. Technical conventions

### Backend

- **Async end to end**: `AsyncSession`, `async def`, async drivers (`asyncpg`). Never mix sync and async.
- **Layer separation**: routers → services/repositories → models. Routers do not query the DB directly.
- **Pydantic**: separate input and output schemas (`XCreate`, `XUpdate`, `XRead`). Never return SQLAlchemy models directly.
- **Ownership and permissions**: in a collaborative app, every query on a resource must validate access (project membership) **in the same query**, not in a later `if`. No IDOR.
- **Errors**: `HTTPException` with the correct status code (201 on creation, 204 on delete, 403 vs 404 as appropriate). No `except Exception: pass`.
- **No business logic in models** unless we agree on it.
- Do not add new dependencies without proposing it first and justifying why what we already have isn't enough.

### Database and migrations

- **Every schema change goes through Alembic.** Never manual DDL, never `create_all()` in production.
- Autogenerated migrations **are reviewed before applying**: `alembic revision --autogenerate` frequently produces noise (indexes, constraints, types).
- Never edit or delete a migration that has already been applied. Create a new one.
- Before proposing a model change, tell me what migration it implies.

### Tests

- If a fix should have a test, tell me — but **do not write it** unless I ask.

## 7. Commands and operations

**Free to run:** reading files, `git status`, `git diff`, `git log`, running tests, starting the local server.

**Require my explicit ok:** installing dependencies, creating/applying migrations, `git add/commit`, creating branches, modifying `.env`, `alembic.ini`, `docker-compose.yml`, or any config file.

**Never, under any circumstance:** `git push --force`, `git reset --hard`, deleting branches, `DROP TABLE/DATABASE`, `alembic downgrade` against real data, deleting files, touching credentials, or committing secrets.

## 8. Git

### Commit authorship — important

- **Never add co-author trailers.** No `Co-Authored-By: Claude <noreply@anthropic.com>`, no `Co-Authored-By: Copilot`, no equivalent for any AI tool.
- **Never add generation footers** such as "Generated with Claude Code", "🤖 Generated with...", or any signature/emoji marking the commit as AI-made.
- Commits must be authored **solely by me**, so no bot or assistant ever shows up in the GitHub contributors/collaborators list.
- The commit message body ends with the last line of actual content. Nothing after it.

### Style

- Commit messages in English, conventional format: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`.
- One commit = one logical change. No giant commits.
- I decide when to commit. You may propose the message.
